# Sovereign Compliance Verify Action (`Terrygilligan/compliance-audit-verify-action`)

A zero-dependency, open-source GitHub Action that bridges continuous integration pipelines with the Sovereign Compliance and Billing Engine (`compliance-audit.eu`).

## Architectural Guarantees

- **Zero Code Exfiltration:** Source code never leaves your repository. The action evaluates a deployed preview or staging URL — only abstract findings cross the wire, never your code.
- **Inform Aggressively, Block Conservatively:** Builds fail exclusively on unequivocal WCAG 2.2 Level A critical defects (`fail-on: level-a`). Advisory warnings, heuristic notes, and manual-review items generate rich Pull Request comments and step summaries without blocking deployments.
- **Sovereign Partition Routing:** Directs requests to regional compliance nodes (`europe-west1` or `europe-west2`) via the `x-compliance-region` header. The header is a routing claim, never authority — it must match your API key's home partition or the engine refuses with `403 sovereign_partition_mismatch`. Leave `region` empty to let geo-routing pick the node.

## Inputs

| Input | Description | Required | Default |
|---|---|---|---|
| `api-key` | Scoped compliance API key (store as repo secret `COMPLIANCE_API_KEY`). | **Yes** | — |
| `tenant-id` | Bound tenant ID associated with the API key's owner partition. A mismatched tenant produces an opaque `401` by design — there is no safe default. | **Yes** | — |
| `target-url` | Deployed preview or staging URL to scan. | **Yes** | — |
| `region` | Sovereign partition: `europe-west1` or `europe-west2`. Leave blank for geo-routing. | No | `''` |
| `api-base` | Compliance API base endpoint. | No | `https://api.compliance-audit.eu` |
| `tiers` | Audit tiers (`1` = static AST fast-pass, `2` = Playwright + axe-core browser checks). | No | `1,2` |
| `timeout-seconds` | Maximum polling time for the audit job. | No | `600` |
| `poll-interval-seconds` | Poll interval for audit status. | No | `10` |
| `fail-on` | Failure gating threshold: `level-a`, `any-error`, or `never`. | No | `level-a` |
| `comment` | Post/upsert a Markdown summary comment on Pull Requests. | No | `true` |
| `github-token` | Token used for PR commenting. | No | `${{ github.token }}` |
| `verify-chain` | Also call `/v1/tenants/:id/audit/verify` and append the Merkle proof-chain status to the summary. | No | `false` |

## Outputs

| Output | Description |
|---|---|
| `audit-run-id` | The unique audit run identifier generated by the engine. |
| `verdict` | Final execution verdict: `success`, `failed`, or `blocked`. |
| `level-a-failures` | Count of critical WCAG Level A conformance failures. |

## Example Usage

```yaml
name: Compliance Verification

on:
  pull_request:
    branches: [ main ]

jobs:
  audit:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - name: Run Accessibility Compliance Check
        uses: Terrygilligan/compliance-audit-verify-action@v1
        with:
          api-key: ${{ secrets.COMPLIANCE_API_KEY }}
          tenant-id: ${{ secrets.COMPLIANCE_TENANT_ID }}
          region: 'europe-west1'
          target-url: 'https://my-preview-deployment.example.com'
          fail-on: 'level-a'
```

## Prerequisites

- **API key scope:** mint a dedicated key per repository with `assess` + `read` permissions (portal → API Keys). Keep it as the `COMPLIANCE_API_KEY` repository secret.
- **Tier:** the `audit` feature requires a `demo` tier key or above — free-tier keys receive `403 feature_not_in_tier`.
- **Rate limit:** `POST /v1/audit` is capped at 10 runs/hour per caller IP.
- **PR comments** require `pull-requests: write` permission on the job. On forked PRs (read-only `GITHUB_TOKEN`) the comment step no-ops cleanly and the step summary still renders.

## Repo-locked keys (honest disclaimer)

"Repo-locked" is currently a convention, not server-side enforcement: mint one scoped key per repository and store it as that repo's secret. The runner sends an `x-github-repository` claim header with every request so future server-side repo binding can be enforced without changing the action.

## Notes

- PR scans audit a **deployed URL**. For PRs that change the page, pass a real preview-deployment URL (Vercel / Firebase Hosting channel / Netlify deploy preview). Scanning a fixed staging URL validates merged content, not the PR — see `sample-app/` for the GitHub Pages pattern.
- Only the URL and abstract findings cross the wire — the engine never fetches or stores source code.
